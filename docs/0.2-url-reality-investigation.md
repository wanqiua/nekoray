# 0.2 URL 批测与 REALITY 排查

日期：2026-09-29。检查正在运行的 0.2 安装配置与历史记录；隔离进程测试，不修改安装文件、节点配置、系统代理或 TUN。

## 1. 批测失败、单测成功

当前设置：并发 10、每次请求超时 10000 ms、URL `http://cp.cloudflare.com/`。

历史记录确认如下失败随后恢复（节点仅保留本地 ID，不记录地址及凭据）：

| ID | 协议 | 先前错误 | 随后成功耗时 |
|---|---|---|---|
| 1085 | VLESS | context deadline exceeded | 9573 ms |
| 1162 | VLESS | context deadline exceeded | 9681 ms |
| 705 | VLESS | context deadline exceeded | 1217 ms |
| 714 | Hysteria2 | EOF | 585 ms |
| 715 | Hysteria2 | context deadline exceeded | 379 ms |
| 720 | Hysteria2 | context deadline exceeded | 325 ms |
| 987 | VLESS | context deadline exceeded | 151 ms |
| 996 | VLESS | context deadline exceeded | 302 ms |
| 201 | HTTP | context deadline exceeded | 2798 ms |

`go/grpc_server/probe/url.go` 对普通 URL 只请求一次；`ui/mainwindow_grpc.cpp` 将远端错误直接保存为 connection_failure，没有在批次结束后对失败项低并发复核。sing-box 仅针对明确的启动网络重置有窄范围重试，不能覆盖上述所有失败。

因此，失败记录表达的是当次请求失败，不能据此认定节点持续不可用。并发引起的带宽/握手竞争、链路抖动或远端限流均可能影响结果；现有历史没有资源、抓包及服务端证据，不能进一步确定这些因素的占比。两条接近 10 秒的成功记录尤其说明超时余量不足。

使用原安装包两份内核运行：

```powershell
.\tests\acceptance\batch-url.ps1 -CoreDirectory 'C:\AAA\NekoRay_BY_WanQiu-0.2-windows-x64\NekoRay_BY_WanQiu' -Concurrency 10 -NodeCount 24 -Repeat 1
```

结果：36/36 组串行/批测状态一致；24 个健康样本串行 5479 ms、批测 700 ms；实测峰值 10；取消及恢复通过。这是受控回环 RPC/内核测试，不代表已排除 Qt 调度问题，也不替代公网复现。

建议：批次完成后仅对超时、EOF 等瞬时连接失败进行一次低并发复核；保留两次尝试记录及取消语义；不切换内核掩盖错误。界面应区分“本次测试超时/失败”和持续不可用。暂时可将并发调到 3～5、超时调到 15～20 秒，并单独复测失败项；此设置建议尚未在用户全部公网节点上验证。

## 2. 默认分组 vless-reality

节点 ID 30：VLESS + TCP + REALITY + xtls-rprx-vision，指纹 chrome。同一生成配置摘要在旧内核有多次成功记录，0.2 Xray 连续失败。

用当前源码依赖构建的隔离探针读取原节点必要参数，保持服务端地址、端口、UUID、公钥、short ID、SNI、flow 与测试 URL 相同，仅改变指纹或内核：

| 内核 / 指纹 | 结果 |
|---|---|
| Xray 26.3.27-matsuri.1 / chrome | 失败，底层握手 EOF，URL 层表现为 closed pipe |
| Xray / firefox | 同样失败 |
| Xray / hellochrome_120 | 成功 672 ms |
| Xray / hellochrome_106_shuffle | 成功 253 ms |
| sing-box 1.14.0 / chrome | 成功 324 ms |
| sing-box / firefox | 成功 274 ms |

随后按 chrome → hellochrome_120 → chrome → hellochrome_120 顺序再次验证：失败 → 313 ms 成功 → 失败 → 1332 ms 成功。

结论：已定位为新 Xray 的自动浏览器指纹与该 REALITY 服务端/链路之间的握手兼容问题；不是节点失效，也不是只有批测才发生。Xray 的 chrome 当前映射到 Chrome 133，firefox 映射到 Firefox 148；新指纹含 X25519MLKEM768。sing-box 的 REALITY 客户端明确过滤此曲线和 KeyShare。ML-KEM 差异是进一步源码排查的重点，但本次没有仅去掉 ML-KEM 的独立变量实验或服务端日志，不能声称具体拒绝机制已经证实。

可行处理：该节点继续使用 Xray 时将 uTLS 指纹明确设为 `hellochrome_120`；或明确选择 sing-box 并保留 `chrome`。这两条路径已隔离实测成功。不要对所有节点静默替换指纹，也不建议因普通远端失败自动切换内核。
